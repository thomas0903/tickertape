# 0028: C ABI

- **Status:** proposed (the surface becomes stable at v1.0; the owner still has to agree)
- **Date:** 2026-11-19

## Context

The v1.0 interoperability milestone asks for a C ABI with documented ownership, record lifetimes, errors,
threading, durability and versioning, plus a C/C++ example, kept outside the core crate. It will be the base for
bindings in other languages (Go through cgo, Java through the FFM API, C#), so it has to be easy to bind
mechanically and hard to misuse. The Rust API has things C cannot express: lifetimes on borrowed records, an
`unsafe` constructor, closures, `#[non_exhaustive]` enums and structs, and panics. The repository rule so far has
been that `unsafe` code lives only in `crates/tickertape/src/mmap.rs` and `crc.rs`.

## Options considered

1. **C functions inside the core crate** behind a feature: no new crate, but FFI code and its `unsafe` would sit
   next to the format code, and the roadmap asks to keep bindings out of the core.
2. **A separate crate wrapping the public Rust API**, with opaque handles and a generated header. Nothing in the
   core changes; anything the Rust API can't express is left out.
3. **A "C-shaped" mirror of every Rust type** (public structs for configs and reports, an enum per error): easier
   to write, but every public struct is frozen forever and grows only by breaking the ABI.

## Decision

Option 2: a workspace crate `crates/tickertape-ffi` (the name was free on crates.io), built only on the public
`tickertape` API. No core change was needed.

**Artefacts.** `[lib] name = "tickertape"`, `crate-type = ["cdylib", "staticlib"]`: a plain `cargo build` produces
`libtickertape.{so,dylib,a}`, so C code links with `-ltickertape`. The header `include/tickertape.h` is generated by
cbindgen 0.29.4 from the crate's doc comments (cbindgen is a tool, not a dependency: it is MPL-2.0 and stays out of
the dependency graph) and committed; CI regenerates it and fails on any difference. It compiles as C99 and C++11
(tested with `-Wall -Wextra -Werror -pedantic`). The crate carries `[package.metadata.capi]`, so packagers can run
`cargo cinstall` (cargo-c) to install the library with a soname/install name, the header and `tickertape.pc`. A plain
build does not set a soname (Linux) and leaves an absolute install name (macOS); that is fine for building and testing
in place, and `docs/c-api.md` says how to install. The crate refuses to compile with `panic = "abort"` (see Errors).

**Symbol prefix.** `tickertape_` for functions and types, `TICKERTAPE_` for constants. The shorter `tt_` collides
with existing C APIs (ToolTalk's `tt_open`, `tt_free`, ...) and FreeType's `TT_` macros; exported symbols share one
process-wide namespace, so the long prefix is worth its length.

**Surface.** Small and complete for record/replay:
- *Writer:* open with options, `append`, `append_with` (zero-copy, see below), `append_batch`, `checkpoint`,
  `next_seq`, `last_retention_error`, `close`.
- *Reader:* `open` (safe `pread` reader), `open_mapped_unsafe`, `seek`, `next` (borrowed view; `timeout_ns` 0 is
  try-next, positive waits with the configured back-off, negative waits forever), `next_copy` (copy into a caller
  buffer), `read_batch` (many records into one caller buffer), `position`, `close`.
- *Options:* opaque builders `tickertape_writer_options` (segment size, recovery policy, notify, prefault,
  retention), `tickertape_reader_options` (durable-only, notify, back-off) and `tickertape_retention` (limits plus an
  action that must be chosen explicitly; there is no default that deletes).
- *Inspection:* `verify` (summary plus the first problem), `list_segments`, `read_checkpoint`, and
  `retention_apply` (plan-only with `dry_run`). The plan object itself, recovery reports and the `format` module are
  left out; the CLI and the Rust API cover them.

Zero-copy appends use a callback, `int32_t fill(void *user_data, uint8_t *buf, size_t len)`, called once with a
zeroed buffer inside the mapped segment. Reserve/commit (two calls) cannot be built on `Writer::append_with`
without changing the core, because the closure must return before the record is committed. A non-zero return
aborts the append: the shim turns it into an unwind that the core already handles (it zeroes the bytes and syncs the
zeroing, `docs/format.md` → Abandoned writes), and the call returns `TICKERTAPE_E_ABORTED`. Aborting costs a sync,
so it is for exceptional cases.

**Batches** are built only on the existing Rust API (one `append` or `try_next` per record, no core batching).
`append_batch` validates every argument first, so an argument error appends nothing; it then appends in order and
stops at the first failure, returning that error with `*appended` records committed (sequence numbers
`*first_seq .. *first_seq + *appended`). `read_batch` waits up to `timeout_ns` for the first record only, then takes
only what is already committed. A record that does not fit in the remaining buffer is held back and returned first
by the next call (by `TICKERTAPE_E_BUFFER_TOO_SMALL` when it is the first, with the size it needs). If an error
occurs after some records were read, the call returns `TICKERTAPE_OK` with those records and the next call on the
reader returns the error, so a caller that bails out on errors never loses records it was handed.

**Ownership and lifetimes.**
- Every object (writer, reader, the three option builders) is an opaque handle created by a `*_open`/`*_new` call
  and freed by the matching `*_close`/`*_free`. Passing `NULL` to a free or close function does nothing. Options are
  copied by `open`; they can be freed right after.
- A record returned by `tickertape_reader_next` is a borrowed view: its `payload` points into the reader's buffer or,
  for a mapped reader, into the mapping. It is valid until the next call that takes the same reader handle
  (`tickertape_reader_position` excepted) or its close. `next_copy` and `read_batch` copy into caller memory instead.
- Strings returned by the library are either static (`tickertape_version`, `tickertape_status_name`) or thread-local
  (`tickertape_last_error_message`, valid until the next failing call on that thread). Callers never free them.
- `NULL` for a required pointer is detected and returns `TICKERTAPE_E_INVALID_ARGUMENT`. A call on a handle that is
  already inside a call on the same thread (for example from a fill callback) is detected and returns
  `TICKERTAPE_E_BUSY`. Use after close, double close and concurrent calls on one handle from several threads are
  **undefined behaviour** and are not detected: detecting them would need a global handle table or an atomic
  operation on every call, which the hot paths should not pay.

**Errors.** Every function returns `tickertape_status` (`int32_t`): `TICKERTAPE_OK` (0); `TICKERTAPE_NONE` (1),
success with nothing to return (no record committed yet, the timeout passed, the next record isn't covered by a
checkpoint yet, or no valid checkpoint marker); negative values are errors. Each `tickertape::Error` variant has its
own code, `Error::Io` is split into `TICKERTAPE_E_STORAGE_FULL` (`is_storage_full`) and `TICKERTAPE_E_IO`, and each
`CorruptReason` has a code available after `TICKERTAPE_E_CORRUPT`. A failing call also records, per thread, the
code, a message, the OS error number and the corruption reason (errno-like: successful calls leave them alone). A
test reads the core crate's `error.rs` and fails if a variant or reason has no code, because `#[non_exhaustive]`
makes an exhaustive `match` impossible outside the core. Every entry point runs inside `catch_unwind`; a caught panic
returns `TICKERTAPE_E_PANIC` and marks the handle broken (later calls return `TICKERTAPE_E_PANIC`; close still
works). The functions are `extern "C"`, so a panic that escaped anyway would abort, never unwind into C. This needs
`panic = "unwind"`, hence the compile-time check.

**Threading.** A writer or reader handle may be moved to another thread between calls but must not be used by two
threads at once; the caller synchronises. A writer handle is single-threaded in that sense, as `Writer` is `Send` but
not `Sync`. Option builders follow the same rule. Separate readers are independent and can run on separate threads.
Callbacks run on the calling thread. **`fork()`:** handles created before a fork must not be used, or closed, in the
child: a writer's background threads don't exist there, and two processes appending through one writer would corrupt
the journal. The child should open its own handles or `exec`. The library's files are opened with `O_CLOEXEC`, so
an `exec` releases an inherited writer lock; a child that neither execs nor exits keeps the lock held.

**Durability** is named as in the crash contract: `append`, `append_with` and `append_batch` return when records are
*visible*, never claiming durability; `tickertape_writer_checkpoint` makes them *durable*;
`tickertape_reader_options_set_durable_only` gives C13 reads. The header repeats this on each function.

**Mapped reader.** The function is `tickertape_reader_open_mapped_unsafe`, and its header comment starts with the
precondition in a `# Safety` section: while the reader exists, no process other than a tickertape writer may modify
the journal's segment files; truncation raises `SIGBUS`. The safe reader is the one without a suffix.

**Versioning.** `TICKERTAPE_ABI_VERSION` (header) and `tickertape_abi_version()` (library); callers compare them at
start-up. `tickertape_version()` returns the crate version string. Before 1.0 the ABI version is 0 and may change in
any minor release, recorded in the changelog. At 1.0 it becomes 1, the soname becomes `libtickertape.so.1`
(`libtickertape.1.dylib`), and "stable" means: no function, constant or struct field is removed or changes meaning
or layout; additions are new functions, new constants, new option setters and new status codes (callers must treat
an unknown negative status as an error). Configuration that may grow lives behind opaque builders. Output structs
tied to format version 1 records (`tickertape_record`, `tickertape_new_record`, `tickertape_segment_info`,
`tickertape_checkpoint`) are frozen; a new format version would get new types. Report structs that may grow
(`tickertape_verify_report`, `tickertape_retention_report`) start with a `struct_size` field the caller sets to
`sizeof`, and the library writes only the fields that fit. Reserved input fields must be zero.

**`unsafe` outside the two core modules.** An FFI crate cannot avoid `unsafe`: it dereferences raw pointers from C
and exports `#[unsafe(no_mangle)]` symbols. This ADR extends the rule deliberately and only to
`crates/tickertape-ffi`: each `unsafe` block is small and has a `// SAFETY:` comment, each `unsafe extern "C" fn`
documents its contract in a `# Safety` section that cbindgen copies into the header, and the core crate gets no FFI
code. `CONTRIBUTING.md` and `docs/playbooks/add-feature.md` say so.

**Distribution.** `publish = false`: a crate on crates.io adds nothing for C users, who need the built library and
header. ADR [0031](0031-bindings-and-install-channels.md) makes a C library archive per platform (shared and static
library, header, pkg-config file) a v1.0 install channel; the artefact names and the cargo-c layout here are chosen
to fit it, but adding the archive to the release workflow is follow-up work (the four release targets, and a soname
decided before 1.0). The small RAII wrapper in `examples/c/tickertape.hpp` is a starting point for the header-only C++
binding that ADR 0031 also asks for.

## Consequences

- C, C++ and binding authors get one header and one library; Go, Java and C# bindings can be generated from the header.
- Tests: Rust tests call the `extern "C"` functions (including null and misuse cases and a Miri run of the parts that
  don't touch files); C99 and C++11 programs are compiled against the committed header and run on Linux and macOS,
  under AddressSanitizer and UBSan in CI and Valgrind on Linux; a cross-language fixture checks that a journal written
  through the C ABI reads back identically with the Rust reader and the Python decoder, and that the C reader reads a
  Rust-written journal, across a segment roll and with durable-only reads.
- New docs: `docs/c-api.md`, `examples/c/`. New CI job `ffi` (both platforms) with the header-drift check.
- The ABI is not stable until 1.0; until then breaking changes bump `TICKERTAPE_ABI_VERSION`.
- Follow-ups: the C library archive in the release workflow and the C++ header binding (ADR 0031); whether the crate
  is ever published to crates.io. Windows is out of scope with the core.
