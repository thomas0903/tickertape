# 0028: C ABI

- **Status:** accepted (the surface becomes stable at v1.0); how an aborted fill is carried out amended by
  [0039](0039-aborted-fill-without-unwinding.md) (no unwinding); the metrics sample's threading and unknown values
  amended by [0032](0032-operational-metrics.md) → Bindings
- **Date:** 2026-11-19 (revised the same day after review round 1 of pull request #10)

## Context

The v1.0 interoperability milestone asks for a C ABI with documented ownership, record lifetimes, errors,
threading, durability and versioning, plus a C/C++ example, kept outside the core crate. It will be the base for
bindings in other languages (Go through cgo, Java through the FFM API, C#), so it has to be easy to bind
mechanically and hard to misuse. The Rust API has things C cannot express: lifetimes on borrowed records, an
`unsafe` constructor, closures, `#[non_exhaustive]` enums and structs, and panics. The repository rule so far has
been that `unsafe` code lives only in `crates/tickertape/src/mmap.rs` and `crc.rs`.

## Options considered

1. **C functions inside the core crate** behind a feature: no new crate, but FFI code and its `unsafe` would sit
   next to the format code, and the roadmap asks to keep bindings out of the core.
2. **A separate crate wrapping the public Rust API**, with opaque handles and a generated header. Nothing in the
   core changes; anything the Rust API can't express is left out.
3. **A "C-shaped" mirror of every Rust type** (public structs for configs and reports, an enum per error): easier
   to write, but every public struct is frozen forever and grows only by breaking the ABI.

## Decision

Option 2: a workspace crate `crates/tickertape-ffi` (the name was free on crates.io), built only on the public
`tickertape` API. The core needed one small additive change: `Writer::abandoned_write_error` (and a fault-injection
point), so that a failed clean-up after an aborted fill can be reported (see Errors).

**Artefacts.** `[lib] name = "tickertape"`, `crate-type = ["cdylib", "staticlib"]`: a plain `cargo build` produces
`libtickertape.{so,dylib,a}`, so C code links with `-ltickertape`. The header `include/tickertape.h` is generated by
cbindgen 0.29.4 from the crate's doc comments (cbindgen is a tool, not a dependency: it is MPL-2.0 and stays out of
the dependency graph) and committed; CI regenerates it and fails on any difference. It compiles as C99 and C++11
(the tests build it as C99, C11, C++11 and C++20 with `-Wall -Wextra -Werror -pedantic`). The crate carries `[package.metadata.capi]`, so packagers can run
`cargo cinstall` (cargo-c) to install the library with a soname/install name, the header and `tickertape.pc`. A plain
build does not set a soname (Linux) and leaves an absolute install name (macOS); that is fine for building and testing
in place, and `docs/c-api.md` says how to install. The crate refuses to compile with `panic = "abort"` (see Errors),
except in one test's own build, which passes the private compiler cfg `tickertape_test_panic_abort` (ADR 0039).

**Symbol prefix.** `tickertape_` for functions and types, `TICKERTAPE_` for constants. The shorter `tt_` collides
with existing C APIs (ToolTalk's `tt_open`, `tt_free`, ...) and FreeType's `TT_` macros; exported symbols share one
process-wide namespace, so the long prefix is worth its length.

**Surface.** Small and complete for record/replay:
- *Writer:* open with options, `append`, `append_with` (zero-copy, see below), `append_batch`, `checkpoint`,
  `next_seq`, `last_retention_error`, `close`.
- *Reader:* `open` (safe `pread` reader), `open_mapped_unsafe`, `seek`, `next` (borrowed view; `timeout_ns` 0 is
  try-next, positive waits with the configured back-off, negative waits forever), `next_copy` (copy into a caller
  buffer), `read_batch` (many records into one caller buffer), `position`, `close`.
- *Options:* opaque builders `tickertape_writer_options` (segment size, recovery policy, notify, prefault,
  retention), `tickertape_reader_options` (durable-only, notify, back-off) and `tickertape_retention` (limits plus an
  action that must be chosen explicitly; there is no default that deletes).
- *Inspection:* `verify` (summary plus the first problem), `list_segments`, `read_checkpoint`, and
  `retention_apply` (plan-only with `dry_run`). The plan object itself, recovery reports and the `format` module are
  left out; the CLI and the Rust API cover them.

Zero-copy appends use a callback, `int32_t fill(void *user_data, uint8_t *buf, size_t len)`, called once with a zeroed
buffer inside the mapped segment (`buf` is NULL when `len` is 0). Reserve/commit (two calls) cannot be built on
`Writer::append_with` without changing the core, because the closure must return before the record is committed; it can
be added later. A non-zero return aborts the append: the shim declines the record through the core's
`Writer::try_append_with`, which zeroes the bytes and syncs the zeroing (`docs/format.md` → Abandoned writes) and
returns without unwinding, and the call returns `TICKERTAPE_E_ABORTED` (ADR 0039; until then the shim turned the
non-zero return into an unwind out of `Writer::append_with`'s closure). Aborting costs a sync, so it is for exceptional
cases. The callback type is `extern "C-unwind"` (cbindgen emits the same C typedef), so a foreign unwind through it is
not undefined behaviour; but Rust leaves it unspecified whether a foreign exception that reaches `catch_unwind` aborts
the process or is caught as an opaque error. An exception escaping the callback is therefore documented as unsupported,
with process termination possible, and callbacks must catch their own exceptions; `longjmp` out of the callback is
undefined. A test records the observed outcome (an abort, on the platforms tested); it documents behaviour, not a
promise. Using `C-unwind` also lets a Rust panic in a callback (only possible from Rust callers) reach the panic guard,
which the tests use to exercise the broken-handle path through a real function.

**Batches** are built only on the existing Rust API (one `append` or `try_next` per record, no core batching).
`append_batch` validates every argument first (the message names the failing record's index), so an argument error
appends nothing; it then appends in order without allocating and stops at the first failure, returning that error
with `*appended` records committed (sequence numbers `*first_seq .. *first_seq + *appended`). `*appended` is stored
after each commit, so it stays right even if a later append panics. The array's size in bytes is checked against
`isize::MAX` before a slice is formed.

`read_batch` waits up to `timeout_ns` for the first record only, then takes only what is already committed. A record
that does not fit in the remaining buffer is held back and returned first by the next call (by
`TICKERTAPE_E_BUFFER_TOO_SMALL` when it is the first, with the size it needs). If an error occurs after some records
were read, the call returns `TICKERTAPE_OK` with those records and **defers** the error, so a caller that bails out
on errors never loses records it was handed. The deferred error is returned by the next read call of any kind
(`next`, `next_copy` or `read_batch`), which clears it. A successful `seek` discards a held-back record and a
deferred error, because they belong to the old position; a failed seek leaves both in place, because the core's
cursor does not move either (it only invalidates a borrowed view, as every call does). The reader never advances past
the failing position, so a persistent error (corruption) is returned again by the calls after the deferred one,
until the caller seeks elsewhere. `position` reports the held-back record's sequence number.

**Ownership and lifetimes.**
- Every object (writer, reader, the three option builders) is an opaque handle created by a `*_open`/`*_new` call
  and freed by the matching `*_close`/`*_free`. Passing `NULL` to a free or close function does nothing. Options are
  copied by `open`; they can be freed right after.
- A record returned by `tickertape_reader_next` is a borrowed view: its `payload` points into the reader's buffer or,
  for a mapped reader, into the mapping. It is valid until the next call that takes the same reader handle
  (`tickertape_reader_position` excepted) or its close. `next_copy` and `read_batch` copy into caller memory instead.
  An empty payload is always returned as NULL, never as Rust's dangling non-null pointer. Read-only calls
  (`position`, `next_seq`, `last_retention_error`) take only a shared reference to the handle's state
  (`Handle::with_ref`), so they cannot invalidate a view however the core stores its buffers; a Miri test shows the
  difference.
- **Memory regions.** Input and output memory of one call must not overlap, inputs (payloads, record arrays, paths)
  must stay unmodified by any thread until the call returns, and output storage belongs to the caller. Each
  function's `# Safety` section names its regions, so the rule reaches the header. Where the check is cheap (append,
  append_batch with each payload, next_copy, read_batch, list_segments), an overlap returns
  `TICKERTAPE_E_INVALID_ARGUMENT` before anything is written; elsewhere it is undefined behaviour. (Review found that
  an output inside an input could zero a length before validation, or overwrite returned payloads under an `OK`.)
- Allocation failure aborts the process, as in any Rust program: the `*_new` and open functions never return NULL or
  an error for lack of memory, and the header says so.
- A close that returns any status other than `TICKERTAPE_E_BUSY` (including `TICKERTAPE_E_PANIC`) has freed the
  handle; retrying it would free twice.
- Strings returned by the library are either static (`tickertape_version`, `tickertape_status_name`) or thread-local
  (`tickertape_last_error_message`, valid until the next failing call on that thread). Callers never free them.
- `NULL` for a required pointer is detected and returns `TICKERTAPE_E_INVALID_ARGUMENT`. A call on a handle that is
  already inside a call on the same thread (for example from a fill callback) is detected and returns
  `TICKERTAPE_E_BUSY`. Use after close, double close and concurrent calls on one handle from several threads are
  **undefined behaviour** and are not detected: detecting them would need a global handle table or an atomic
  operation on every call, which the hot paths should not pay.

**Errors.** Every function returns `tickertape_status` (`int32_t`): `TICKERTAPE_OK` (0); `TICKERTAPE_NONE` (1),
success with nothing to return (no record committed yet, the timeout passed, the next record isn't covered by a
checkpoint yet, or no valid checkpoint marker); negative values are errors, assigned downwards from -1.
`TICKERTAPE_E_UNKNOWN` is -255 (mirroring `TICKERTAPE_CORRUPT_UNKNOWN = 255`), so codes added later never land
beyond it. Each `tickertape::Error` variant has its
own code, `Error::Io` is split into `TICKERTAPE_E_STORAGE_FULL` (`is_storage_full`) and `TICKERTAPE_E_IO`, and each
`CorruptReason` has a code available after `TICKERTAPE_E_CORRUPT`. A failing call also records, per thread, the
code, a message, the OS error number and the corruption reason (errno-like: successful calls leave them alone). A
test reads the core crate's `error.rs` and fails if a variant or reason has no code, because `#[non_exhaustive]`
makes an exhaustive `match` impossible outside the core. Every entry point runs inside `catch_unwind`; a caught panic
returns `TICKERTAPE_E_PANIC` and marks the handle broken (later calls return `TICKERTAPE_E_PANIC`; close still
works). The functions are `extern "C"`, so a panic that escaped anyway would abort, never unwind into C. This needs
`panic = "unwind"`, hence the compile-time check.

The last-error state is per operating-system thread. Bindings whose runtime moves tasks between OS threads (Go
goroutines, Java virtual threads) must read it in the same foreign call sequence as the failing call, on the same
OS thread: in Go, a C shim in the cgo preamble that makes the call and captures the code, message, OS error and
corruption reason together, or `runtime.LockOSThread` (a cgo probe on two OS threads confirmed that a migrated
goroutine reads the other thread's state). The message is UTF-8, with non-UTF-8 file names replaced lossily.

**A failed clean-up after an aborted fill.** If zeroing the bytes of an aborted fill cannot be synced, the core
poisons the writer and refuses further appends. The C call that aborted returns `TICKERTAPE_E_IO` with the OS error
and a message saying that the clean-up failed, instead of `TICKERTAPE_E_ABORTED`, which means a clean abort. Later
appends return `TICKERTAPE_E_IO` with the same OS error and a message that names the cause, and checkpoints return
`TICKERTAPE_E_DURABILITY_LOST` with a message about the clean-up rather than an earlier checkpoint. The code is
`TICKERTAPE_E_IO` even when the OS error is `ENOSPC` or `EDQUOT` (as `fsync` returns on a full APFS volume), and this
is frozen at 1.0: `TICKERTAPE_E_STORAGE_FULL` promises that an append can be retried once space is available, and a
refused append never can. In the core, the stored error and every refused append carry the OS error wrapped in an
`io::Error` of kind `Other`, so `Error::is_storage_full()` is false and the OS error stays reachable as the inner
error; the C ABI reports it through `tickertape_last_error_os_code()`. A failed clean-up is a storage incident in the
crash contract's terms for a failed checkpoint in the same boot: the durability of everything written since the last
successful checkpoint is unknown, and reopening gives a usable writer but no guarantee about that tail across a power
loss (after a write-back failure the page cache can hold the zeroed bytes as clean pages while the disk holds the
stale ones, and recovery has no reason to rewrite zeros). Recovery is unchanged. This needed
`Writer::abandoned_write_error()` in the core (the error is stored there) and a corrected `Error::DurabilityLost`
message; tests reproduce it for `EIO` and `ENOSPC` with the `fault-injection` feature.

**Threading.** A writer or reader handle may be moved to another thread between calls but must not be used by two
threads at once; the caller synchronises. A reader blocked with `TICKERTAPE_WAIT_FOREVER` cannot be interrupted, and
closing it from another thread is undefined behaviour, so bindings that offer cancellation loop with a finite
timeout. Timeouts bound only the wait for a record: validation, catching up after a seek and file I/O can take
longer. A writer handle is single-threaded in that sense, as `Writer` is `Send` but
not `Sync`. Option builders follow the same rule. Separate readers are independent and can run on separate threads.
Callbacks run on the calling thread. **`fork()`:** handles created before a fork must not be used, or closed, in the
child: a writer's background threads don't exist there, and two processes appending through one writer would corrupt
the journal. A child of a multithreaded process (a writer normally has a helper thread) may call only
async-signal-safe functions before `exec`, and opening a handle allocates, so a child opens its own handles after
`exec`, and a child that does not `exec` must not use the library at all. The library's files are opened with
`O_CLOEXEC`, so an `exec` releases an inherited writer lock; a child that neither execs nor exits keeps the lock
held.

**Durability** is named as in the crash contract: `append`, `append_with` and `append_batch` return when records are
*visible*, never claiming durability; `tickertape_writer_checkpoint` makes them *durable*;
`tickertape_reader_options_set_durable_only` gives C13 reads, which survive a power loss only under the crash
contract's storage assumptions and if no checkpoint failed earlier in the same boot. The header repeats this on each
function.

**Mapped reader.** The function is `tickertape_reader_open_mapped_unsafe`, and its header comment starts with the
precondition in a `# Safety` section: while the reader exists, no process other than a tickertape writer may modify
the journal's segment files; truncation raises `SIGBUS`. The safe reader is the one without a suffix.

**Versioning.** The header defines `TICKERTAPE_ABI_VERSION`, `TICKERTAPE_VERSION_MAJOR`, `_MINOR`, `_PATCH` and
`TICKERTAPE_VERSION_NUMBER` (`MAJOR * 1000000 + MINOR * 1000 + PATCH`); the library returns its own values from
`tickertape_abi_version()` and `tickertape_version_number()` (and `tickertape_version()` the string). The version
macros are literals, because cbindgen cannot evaluate `env!`; a compile-time assertion fails the build if they differ
from the crate version.

- **Before 1.0, ABI version 0 means unstable.** Any release may change the ABI (the changelog says so), and the ABI
  version stays 0, so it cannot tell two pre-1.0 libraries apart. A program or binding must therefore require the
  exact library version: `tickertape_version_number() == TICKERTAPE_VERSION_NUMBER`.
- **From 1.0, compatible means the ABI version is equal and the library's version is at least the header's.** The
  ABI version becomes 1 and the soname `libtickertape.so.1` (macOS install name `libtickertape.1.dylib`). "Stable"
  means: no function, constant or struct field is removed or changes meaning or layout; additions are new functions,
  new constants, new option setters, new status codes (callers must treat an unknown negative status as an error) and
  new fields at the end of extensible structs. A program built against 1.3 may use what 1.3 added, so it refuses a
  1.0 library by the version comparison, even though the ABI version matches. A break would be 2.0 with ABI version 2
  and a new soname.

The start-up check `abi == TICKERTAPE_ABI_VERSION && (TICKERTAPE_ABI_VERSION == 0 ? lib == TICKERTAPE_VERSION_NUMBER
: lib >= TICKERTAPE_VERSION_NUMBER)` covers both periods; the header, the docs and every example use it.

Configuration that may grow lives behind opaque builders. Output structs tied to format version 1 records
(`tickertape_record`, `tickertape_new_record`, `tickertape_segment_info`, `tickertape_checkpoint`) are frozen; a new
format version would get new types. Reserved input fields must be zero.

**Extensible structs** (`tickertape_verify_report`, `tickertape_retention_report`) start with a fixed-width
`uint64_t struct_size` (a `size_t` followed by 64-bit fields would leave padding on 32-bit targets, and is awkward
in Java's memory layouts). Each has a minimum size, its size in the first stable release (72 and 32 bytes), below
which the call returns `TICKERTAPE_E_INVALID_ARGUMENT`. The library writes `min(struct_size, its own size)` bytes and
stores the number of bytes it filled back into `struct_size`. A program built against an older, smaller struct
therefore works with a newer library, and a program built against a newer, larger struct checks `struct_size` after
the call before reading a field added later, which an older library leaves unwritten.

**Catching layout and signature breaks.** Regenerating the header from the code cannot catch a break, because the C
tests are recompiled against whatever it says. So the Rust code asserts at compile time the size and every field
offset of each `repr(C)` struct, and the C test asserts the same values with `sizeof` and `offsetof`: swapping or
resizing a field fails one side. And CI compares the header with a committed baseline of frozen declarations,
`crates/tickertape-ffi/abi/tickertape-baseline.h`, with `.github/scripts/check_abi_baseline.py`. The baseline has no
declarations before 1.0; the release checklist makes the header as shipped the new baseline at 1.0 and at every
later stable release, so that a declaration added in a minor release is frozen from that release on (comparing only
with 1.0 would let a function added in 1.1 disappear in 1.2). From then on, removing or changing a baseline
function, typedef, constant or enumerator, or changing a frozen struct, fails CI, while additions pass (extensible
structs may only grow at the end, and the version macros may change).

**`unsafe` outside the two core modules.** An FFI crate cannot avoid `unsafe`: it dereferences raw pointers from C
and exports `#[unsafe(no_mangle)]` symbols. This ADR extends the rule deliberately and only to
`crates/tickertape-ffi`: each `unsafe` block is small and has a `// SAFETY:` comment, each `unsafe extern "C" fn`
documents its contract in a `# Safety` section that cbindgen copies into the header, and the core crate gets no FFI
code. `CONTRIBUTING.md` and `docs/playbooks/add-feature.md` say so.

**Operational metrics** (amended 2026-11-20, ADR [0032](0032-operational-metrics.md) → Bindings). The status
sample is an opaque handle that is immutable after creation, so the functions that take a
`const tickertape_journal_status *` may run on several threads at once; this is the one exception to the rule that a
handle is used by one thread at a time, and the header says so. Optional `uint64_t` values of the metrics structs use
the sentinel `TICKERTAPE_UNKNOWN` (`UINT64_MAX`) rather than a flag per field; their enums carry the reason.

**Distribution.** `publish = false`: a crate on crates.io adds nothing for C users, who need the built library and
header. ADR [0031](0031-bindings-and-install-channels.md) makes a C library archive per platform (shared and static
library, header, pkg-config file) a v1.0 install channel; the artefact names and the cargo-c layout here are chosen
to fit it, but adding the archive to the release workflow is follow-up work (the four release targets). The 1.0 soname is decided above; the release checklist verifies
the soname and install name in the packaged library and links a program against the installed package. The small RAII wrapper in `examples/c/tickertape.hpp` stays an example; the official header-only C++
binding that ADR 0031 asks for is a separate follow-up.

## Consequences

- C, C++ and binding authors get one header and one library; Go, Java and C# bindings can be generated from the header.
- Tests: Rust tests call the `extern "C"` functions (including null, overlap and misuse cases and a Miri run of the
  parts that don't touch files); C99/C11 and C++11/C++20 programs are compiled against the committed header and run
  on Linux and macOS,
  under AddressSanitizer and UBSan in CI and Valgrind on Linux; a cross-language fixture checks that a journal written
  through the C ABI reads back identically with the Rust reader and the Python decoder, and that the C reader reads a
  Rust-written journal, across a segment roll and with durable-only reads.
- New docs: `docs/c-api.md`, `examples/c/`. New CI job `ffi` (both platforms) with the header-drift and ABI-baseline
  checks.
- The ABI is not stable until 1.0; until then `TICKERTAPE_ABI_VERSION` stays 0 and programs require the exact library
  version (see Versioning).
- Follow-ups: the C library archive in the release workflow and the C++ header binding (ADR 0031); whether the crate
  is ever published to crates.io. Windows is out of scope with the core.
