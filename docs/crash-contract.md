# Crash contract

Status: **accepted** (M1, approved by the owner on 2026-10-31). This document says exactly what
tickertape guarantees when things go wrong, on each supported platform, and which test checks each guarantee. A
guarantee without a passing test is marked **untested**, and nothing is claimed beyond what is written here.
Rationale: ADRs [0004](decisions/0004-durability-levels.md), [0007](decisions/0007-checkpoint-marker-and-recovery.md),
[0035](decisions/0035-recovery-preserves-a-committed-tail.md) and, for background checkpoints,
[0038](decisions/0038-background-checkpoints.md), for seek indexes,
[0045](decisions/0045-sparse-seek-index.md), for what retention reads,
[0051](decisions/0051-retention-reads-what-it-needs.md), for empty slots,
[0050](decisions/0050-empty-slot-in-history.md), and, for a marker its segment's records do not reach,
[0056](decisions/0056-marker-beyond-its-records.md).
Byte-level details: [`format.md`](format.md).

Supported: Linux (x86-64, aarch64) and macOS (aarch64), on a **local** filesystem (Linux: ext4, xfs, btrfs; macOS:
APFS). Network filesystems, Windows and multiple writers are not supported.

## Two levels: visible and durable

| Level | Reached when | What it means |
|---|---|---|
| **Visible** | `Writer::append` returns `Ok(seq)` | The record is in the shared page cache. Readers in other processes on the same host can read it, and it survives the *writer process* dying. It is **not** on stable storage |
| **Durable** | `Writer::checkpoint` returns `Ok(())`, or a background checkpoint requested with `Writer::request_checkpoint` has finished (`Writer::checkpoint_progress` reports a durable marker whose `next_seq` is at least the value the request returned) | Every record appended before the call (for a background checkpoint: before the request) is on stable storage, under the storage assumptions below |

Visibility is not durability. A reader can see, and act on, a record that a later power loss erases, and the writer
then reuses that sequence number for a different record. Applications that must never act on a record that could
disappear should open their readers with `ReaderConfig::durable_only(true)` (ADR 0010; CLI: `--durable-only`), which
returns only records covered by the last successful checkpoint (C13).

### What `checkpoint()` does

Everything written since the last successful checkpoint is "dirty": records and seals in every segment touched
(including segments the writer has already rolled past; see "Segments the writer no longer holds" below), files and
directories created or renamed, and repairs made at open. A new writer treats everything after the current
checkpoint marker as dirty, including records an earlier writer appended but never checkpointed.

| Step | Linux | macOS |
|---|---|---|
| 1. Data | `msync(MS_SYNC)` on each dirty range of a segment the writer still holds, then `fdatasync` on each dirty segment | `msync(MS_SYNC)` on each dirty range, then `fsync` on each dirty segment |
| 2. Names | `fsync` on the journal directory, `quarantine/`, and the parent of any directory the writer created, if any entry in them changed | `fsync` on the same directories |
| 3. Barrier | (the `fdatasync`/`fsync` calls above already flush the device cache on filesystems mounted with barriers, the default) | `fcntl(F_FULLFSYNC)` on the last dirty segment, after all of the above. It asks the drive to flush its whole write cache, which covers the earlier writes and directory updates too |
| 4. Marker | Write the next `checkpoint` slot with `pwrite`, then `fdatasync` it | Write the next `checkpoint` slot with `pwrite`, then `fcntl(F_FULLFSYNC)` on it |

The marker file itself is created, synced, and its directory entry synced when the journal is created, so step 4
only ever overwrites a slot in an existing file. If something cut the marker short, the writer leaves it short at
open (observers take a full-length marker's modification time as the time of the last checkpoint, ADR 0032), and step
4 may then extend the file to reach the slot; after step 4 succeeds, a fifth step extends the marker to its full
length and syncs it (best effort: a marker left short is still valid, and a later checkpoint tries again).

**Background checkpoints** (`Writer::request_checkpoint`, ADR 0038) run the same steps on the writer's checkpoint
thread while appends continue. "Dirty" then means dirty when the checkpoint was requested: the request takes the
writer's dirty ranges, files and directories as they are and the marker names the writer's position at that moment
(segment, offset, next sequence number); what is appended or created afterwards, including segments the writer rolls
into while the checkpoint runs and their directory entries, belongs to the next checkpoint. One checkpoint runs at a
time, in request order (requests made while one waits join it), and `checkpoint()` waits for them before its own, so
marker generations still increase by one per marker written. The thread is joined when the writer is dropped, after it
has finished the requested checkpoints and before the lock is released.

Every segment the writer has linked before a checkpoint's request is one of the dirty segments of step 1, whose
`fdatasync`/`fsync` makes its header durable: a roll itself does not sync the new segment (ADR 0038 → Rolls without a
sync; C8 has what recovery does when a crash kept such a header from the disk). On Linux the writer may also start
write-back early (`WriterConfig::early_writeback`, `sync_file_range(SYNC_FILE_RANGE_WRITE)` behind the write position,
up to the 128 KiB boundary below it from 1.1). That makes nothing durable and changes none of the steps above: step 1
writes back and waits for every dirty page whether early write-back reached it or not; an I/O error from it poisons the
writer as a failed step 1 would, and is returned once, by the next checkpoint (which writes no marker) or the next
`request_checkpoint`, `checkpoint_progress` or `close`, also when no checkpoint is pending.

**Segments the writer no longer holds.** Between checkpoints each dirty list (the writer's own, and that of each
background checkpoint requested and not yet run) keeps the file and mapping of only its four most recent segments;
older ones, whether it rolled past them or recovery inherited them, are remembered by absolute path (the journal
directory is made absolute at open, so a later change of the working directory does not matter), file identity
(device and inode, read before the file is closed) and range, and the checkpoint that covers them opens them again for
step 1 (ADR 0038 → Bounded open segments). This is
enough because the data is in the file's page cache, not in a descriptor or a mapping: a store through a shared mapping
dirties the file's cached page, and unmapping keeps it dirty, so on Linux `fdatasync` on a newly opened descriptor
writes back every dirty page of the file and waits, and reports a write-back error recorded on the file that no
descriptor of it has observed yet (the kernel's `errseq` rule: a descriptor opened after such an error still sees it
once); there `msync(MS_SYNC)` is a data sync of the same pages and adds nothing. On macOS the writer maps the
reopened file again and calls `msync(MS_SYNC)` on the range before `fsync`, so that pages dirtied through the old
mapping are written back as they were before; step 3 is unchanged. Such a segment is after the marker, so retention
does not remove it (C14); if it is gone anyway (removed by hand), or the file at its path is not the one the writer held
(replaced under the same name; told by device and inode number, so a file removed and created again is not told
apart where the file system gives it the removed file's inode number), the checkpoint fails as a failed sync does, before writing a marker, and poisons the
writer. **The limit:** for such a segment the checkpoint does not report a write-back error that the kernel no longer
remembers (while no descriptor or mapping of the file was open it may have evicted the cached inode, and the error with
it) or that another descriptor of the file already observed (a sync through it reported the error, so a newly opened
descriptor is not told); the checkpoint then succeeds although some of that segment's records may not be durable.

The marker is written only after steps 1–3 succeed, so it never points past data whose sync reported a failure; for a
segment the writer no longer holds, a failure can go unreported (the limit above). On macOS,
plain `fsync` does not flush the drive's write cache; `F_FULLFSYNC` does, and is much slower. tickertape always uses
it, and if it isn't supported (`ENOTSUP`), `checkpoint()` fails rather than claiming less.

**Errors are sticky.** If any step fails, `checkpoint()` returns the error and the writer becomes **poisoned**:
every later `checkpoint()` fails with `Error::DurabilityLost`, while appends continue to work (visibility is
unaffected). This is because on Linux a failed `fsync` can mark the dirty pages clean without writing them, so a
later successful call proves nothing. A background checkpoint that fails poisons the writer the same way; its error is
returned once, by the next `request_checkpoint`, `checkpoint_progress`, `checkpoint` or `close`, and `DurabilityLost`
by every later one (`Writer::metrics().poisoned` is true from the moment it failed). A checkpoint queued behind it is
dropped, and no marker is written after a failed sync of the writer's data, by either thread. A new writer opened in the same boot cannot detect this either: **after a
checkpoint error, records written before it may not be durable even if a later writer's checkpoint succeeds.** Treat
a checkpoint error as an incident.

The same holds when the writer cannot sync the zeroing of an abandoned write (a fill closure that panicked, or a
`try_append_with` fill closure that declined; `format.md` → Abandoned writes). That writer refuses appends as well as
checkpoints (`Writer::abandoned_write_error`), and the durability of everything written since its last successful
checkpoint is unknown, also for a later writer in the same boot.

## Storage assumptions for durability

The durable level holds only if: (a) the filesystem and drive honour the sync calls above (no lying write caches);
(b) a sector or filesystem block that has been made durable is not damaged by an interrupted later write *to the
same block*. Records are small and packed, so a checkpointed record often shares a block with records appended
after the checkpoint. Drives with power-loss protection, and filesystems with copy-on-write data blocks
(btrfs, APFS), avoid in-place rewrites of durable blocks; ext4 and xfs in their default modes rewrite blocks in place
and rely on the drive's sector-write atomicity. If (b) fails, the checkpointed records in that block are lost.
Recovery does not re-read data before the checkpoint marker, except the one record right before the marker's
position, so it won't necessarily notice; readers and `tickertape verify` detect the damage by checksum when they
reach it, and an emptied commit word by the marker that covers it (C11). Damage to that last covered record makes the
writer refuse to open (C11, ADR [0056](decisions/0056-marker-beyond-its-records.md)).

## Guarantees by failure

"Committed" means the record's commit word was stored (`format.md` → Publication); `append` returning `Ok` implies
committed. History deliberately removed by a retention policy or `tickertape archive` is no longer part of the
journal; the durability and restart guarantees below apply to retained history.

Before it scans, an open creates the lock file if it is missing and writes its PID into it (best effort: a failure is ignored), removes stale temporary names (`*.tape.tmp`, the prepared spare), creates the checkpoint file if it is missing (an open leaves a marker that is shorter than its full length as it is), and, once the marker's position has been validated, removes the seek indexes of the segments recovery may change (`format.md` → Recovery, step 2a; C15; they can be rebuilt, and a dangling marker refuses the open with every one left). A marker is dangling when its segment is missing, its offset is invalid, or the segment's records do not reach its position: the record `next_seq - 1` is not there, valid and ending exactly at the marker's offset (at offset 64: `next_seq` is not the segment's base). That is never left by a writer and a crash on storage that meets the assumptions above, outside the exceptions C7 states (the data is durable before its slot is written, C7, and recovery never changes a byte before the marker); it follows from segments restored from a backup older than the marker, from damage to the last covered record, from storage that lost a flushed write, or from a write-back error that went unreported (C7's exceptions). The open is then refused under either policy, with `DanglingCheckpoint`, before anything else is changed (it reports such a marker at the segment and the marker's offset, a missing segment or an invalid offset at the `checkpoint` file); no policy falls back to the other slot or appends after the records that are there (ADR [0056](decisions/0056-marker-beyond-its-records.md); `operations.md` → After a crash says what to do). When it then refuses, it keeps what recovery did in the scan before it reached the corruption it reports, up to the first segment whose header never reached the disk (C8): the clean-ups a process crash needs (a zeroed torn tail; a seal written in place after a crash between publishing a successor and sealing, which can be the seal in front of a corrupt successor; a created missing successor), and the zeroing of (3), including where it removed published records. From that segment on, `Fail` holds back every change: the header it would restore (or the file it would replace) and every change the scan decides after it (zeroing, seals, created successors). The scan continues as if they had been made, and they are made, in the order decided, only after the last point where the open can refuse (the check for disconnected segments). A refused open makes none of them, and an open that fails with an I/O error while making them keeps the ones made so far; either removes the segments it prepared under temporary names and did not publish (a replacement, a created successor; one it could not remove is removed by the next open). So a refusal that comes after recovery decided to restore a header makes no change decided from then on, including the seal in front of that segment. Each held change is the change `Quarantine` makes at the same point, so an open interrupted between two of them leaves a journal the next open recovers to the same end (`tests/recovery.rs::interrupted_held_changes_are_finished_by_the_next_open`). At an empty commit word at `P`, expecting sequence number `S`, recovery decides in this order (ADR 0035 → "How recovery tells them apart", "Work bound", "Damage around a seal"). (1) When a segment for exactly `S` exists, is not the segment being scanned (at a segment's first record slot `S` is its own base), has not been scanned, and the writer opens and maps it successfully (a valid header alone is not enough), `P` is where the seal belongs and nothing else is consulted. Such a segment "does not open" (below) only when it is itself invalid: the writer's open reports it as corrupt (a file shorter than a header, an invalid header, a size or base that does not match) or as an unsupported format version. Any other error opening, reading or mapping it (an I/O error such as `EACCES` on files restored read-only, `EMFILE`, `ENOMEM` or a mapping limit) makes the open fail with that error under either policy, without changing anything at that slot or its successor; what recovery did earlier in the same scan (a seal written in front of an earlier segment, for example) stays (`tests/committed_tail.rs::successor_that_fails_to_open_for_an_io_error_fails_the_open`). If every non-zero byte after `P`'s commit word lies in the seal's CRC word, that word is zeroed and the seal written in place. Otherwise `Quarantine` preserves the bytes after `P`, replaces the segment, then writes the seal (`BadSeal`), and `Fail` refuses with `BadSeal` at `P` without changing a byte of that segment. Where the seal is written (in place, or after the replacement under `Quarantine`), the segment's records before `P` are kept and the scan continues in the successor, which is checked like any other segment. (2) Otherwise, when a byte after `P`'s commit word is non-zero, recovery searches for committed history. First in the segment: a later record that validates with a sequence number its position allows, a valid seal with nothing non-zero after it for such a sequence number at most 128 above `S`, or a stop at the search's work bound before the next candidate is checked. Only the first such find is weighed: when it lies inside a completely written torn frame at `P` (ADR 0035), the segment yields nothing. Then, when the segment yields nothing: a segment with a higher base than `S`, except when a segment for exactly `S` exists, is not the segment being scanned and has not been scanned, but did not open, and every non-zero byte after `P`'s commit word lies in the seal's CRC word. ## Readers, the writer and memory safety

- **`Reader::open` (safe, the default)** doesn't map the files. It reads them with `pread` into a buffer it owns and
  validates the copy, so it is memory-safe whatever other processes do to the files, and it can't receive `SIGBUS`.
  At worst it reports corruption.
- **`Reader::open_mapped` (`unsafe`, zero-copy)** hands out `&[u8]` slices pointing into the shared mapping. The caller
  promises that no process other than a tickertape writer modifies the journal's segment files while the reader
  exists. Each record is first validated from atomic loads of the mapping (each byte loaded once, nothing copied;
  ADR 0027), and a slice into the mapping is created only after it passes. Segments are mapped only on x86-64 and
  aarch64; on other targets `open_mapped` reads with `pread` like `Reader::open`.

  With `ReaderConfig::seek_index(true)` the caller's promise also covers `seek-index/` and the checkpoint marker: no
  process other than a tickertape writer or index builder modifies them. Such a reader uses an index only for a segment
  before the one the marker names, to which no writer stores, and everything it reads of the index, the marker and the
  segment before it has found the indexed record's first 8 bytes in place is read with `pread`, not through the mapping.
  If the marker is damaged later and a recovery changes such a segment in place, the known limitation below applies. With
  the option off nothing changes.

  These guarantees hold **for an intact publication chain**, where every commit word the reader follows is one a
  writer published. A correct writer then never modifies committed bytes: in place, recovery only zeroes bytes
  after an empty slot (never committed, on an intact chain) and writes a seal there, and otherwise replaces or
  moves whole files. So in normal operation, including writer crashes and recovery, the reader's loads race with no
  store, and a returned payload stays equal to the bytes validated.

  **Known limitation (commit words damaged on storage).** A damaged commit word breaks the chain, and a mapped load
  can then touch bytes a writer is storing to without synchronisation. If the writer runs in the same process that is
  a data race in Rust's terms, before any CRC runs; for a writer in another process the language says nothing. Two
  cases:

  - *A non-zero value that no writer stored.* If storage damage enlarges the length in an earlier record's commit word,
    or puts a length or a seal marker into the empty slot at the head, so that the claimed frame reaches bytes a writer
    stores, validating that slot makes the reader load bytes the writer is storing at that moment. The damage can appear
    whether or not a writer runs.
  - *A zeroed commit word.* If storage damage zeroes the commit word of a record that was published but not yet
    covered by a checkpoint, the next writer's recovery usually replaces the segment by a new file when it finds
    evidence of the records after it (or `Fail` refuses), and readers' mappings of the old file do not change. When
    it finds none (C11 (3): damage after which nothing validates, such as the newest record's commit word zeroed), it
    takes the slot for the end of the journal and zeroes that record **and the published records after it** in
    place, under a live zero-copy reader. A payload slice the caller still holds changes, and the reader's later
    commit-word loads meet the new writer's stores.

  The bound that ADR 0048 puts on the loads helps replay and catch-up. A caught-up visible reader tailing the head gets
  nothing from it. As long as the journal's `checkpoint` file holds the markers the writer wrote and no earlier one
  becomes current, neither case concerns a reader with `durable_only(true)`, and the first does not concern a slot below the checkpoint
  position the reader last took (at a segment's open, on reaching that position, and while it waits). Without that, the
  limitation is as stated. (For a durable-only reader one case is left, and it takes two faults: a damaged record that
  ends exactly at the checkpoint position and passes its CRC32C by chance, and a seal marker damaged into the empty slot
  there. The reader then loads the 4 bytes that follow that marker.) Tests:
  `crates/tickertape/src/reader_bound_tests.rs`, `tests/mapped_bound.rs`, the `damaged_frame` models in
  `protocol_model.rs` (loom), and `map_ro_bounded_loads_meet_no_store` (Miri).

  That such loads return some mixture of old and new bytes, which the CRC then rejects, is an assumption about the
  implementation on the supported targets (aligned single-instruction loads), not a guarantee; how likely a chance
  match is depends on the corruption, and a retry can read the same bytes. Every earlier release, which copied the
  same range with the same atomic loads, had the same exposure. ADR
  [0048](decisions/0048-publication-frontier.md) bounds the loads in the first case by the checkpoint marker, for the
  records it covers; it does not close the second for visible readers, where the bytes change because recovery rewrites
  them (ADR 0027 → "Which loads can race").
- **A reader with `ReaderConfig::seek_index(true)`** may start a seek at a record named by a seek index (ADR
  [0045](decisions/0045-sparse-seek-index.md), C15). Every record returned satisfies the five validity rules at its
  position. Records before the landing record are not read, so damage there does not stop the reader. A stale index can
  lead to a wrong record only if a payload holds, at the indexed offset, a complete frame identical in sequence number,
  length and CRC to the record indexed there before. A forged index can do so whenever a payload contains a suitable
  frame. `verify` reports neither; `tickertape index --check` does. Do not enable this where someone who may not write
  the segments can write `seek-index/`.
- **The writer** maps the segments it writes. Its API is safe, following the Rust standard library's position that
  its safety guarantees "only cover what the program itself can do, and not what entities outside the program can
  do to it" (`std::os::unix::io`, on `/proc/self/mem`). Another process writing into or truncating the files the
  writer has mapped is such an outside entity, and can crash or corrupt the writer process.

## Known risks and limits

- **SIGBUS.** The writer and `open_mapped` readers access segments through memory maps. If a segment file is
  truncated by another process, or the storage returns an I/O error on a page fault, the process receives `SIGBUS`
  and dies. tickertape does not catch it. Don't truncate or edit segment files while the journal is in use.
- **btrfs and a full disk.** Preallocation does not protect writes on btrfs: on a full volume they fail with
  `SIGBUS`, or hang with `chattr +C` (C10, measured). APFS behaved like ext4 in the same test. Monitor free space.
- **A reader's view of a record just committed can lag (aarch64 Linux).** On Google Cloud Axion VMs (Neoverse-V2, kernel
  7.0, ext4 and xfs), with an unpaced 1,024 B writer and background checkpoints under memory pressure, and sooner with
  memory compaction forced, readers that map a segment (the zero-copy reader, and an independent mapped reader written
  without tickertape code) saw a record whose commit word was visible while the bytes in its next page still read as
  zeros, although the file held the record intact (a `pread` of it validated) and the writer stores the commit word with
  release ordering after the whole frame. The view caught up within microseconds in the cases timed, but after more
  back-to-back re-reads than a reader made before reporting corruption, so the zero-copy reader reported a record
  checksum mismatch for a record that was published correctly (issue #43; reported at `279f59a`, and the same lag seen
  by the independent reader at `ddcbe49`). A reader now reads a slot that fails validation again for at least 50 ms,
  with growing pauses, before it reports corruption, and returns the record as soon as a re-read validates; real
  corruption is reported that much later, also by `try_next`, and `next_timeout` can pass its timeout by the window. The
  mechanism is not confirmed. The most plausible one is that Linux defers the TLB invalidation of clean pages it
  reclaims or moves, so a reader can keep reading the old copy of a page for a moment while the writer already writes to
  the new one; Linux does this on x86-64 too. It was not seen on x86-64 in the session where it was found, but that run
  ended in a time-out there (issue #45), so its absence is weak evidence; nor on the Apple M4 Linux VMs tried, nor with
  a writer and a reader both written without tickertape code on the same Axion VM. On 2026-11-26 (`benchmarks.md` →
  the two aarch64 observations left open by 1.0.0) the view still lagged on `main`, on an Axion VM with the journal
  larger than RAM: about once in 5 minutes, each time caught up at the first re-read after a pause (within 69 µs; no
  reader of `main` reported corruption), and not in 900 s on an x86-64 VM. At 3 of 10 traced events the kernel's
  reclaim (kswapd) had just removed the frame's pages from the page cache, which fits the deferred invalidation above
  for pages it reclaims (migration waits for the invalidation before it copies); at 6 nothing was removed near the
  write position. With the journal within RAM there was no reclaim and no lag in 1,000 s. Neither account is
  confirmed. A view that stays wrong for longer than the window is still reported as corruption. What holds either
  way: a record is returned only after its bytes have validated (`reader.rs`:
  `a_view_that_catches_up_after_the_back_to_back_re_reads_is_not_reported`). What is known about the file: every slot
  examined held the record intact, and two 600 s runs with the fix validated every record. In long
  runs at `3fea1c0` under forced compaction (an unpaced 1,024 B writer with background checkpoints, a zero-copy and a
  copying reader, 1,075–1,304 s on two Axion and two x86-64 VMs, ext4 and xfs, about 1.5 TB of payload in all), no
  reader reported corruption, both readers reached the writer's last position, and `tickertape verify` of each journal
  from the file afterwards found every retained record valid and the chain intact (`benchmarks.md` → Long verified runs;
  the runs ended with the disk full, because retention fell behind: issue #45). That is the evidence that the writer
  lost no write to this effect, on which issue #43 was closed; it does not identify the mechanism. A lagging view of a
  commit word reads as an empty slot: `try_next` returns `Ok(None)` and `records()` ends although the record is
  committed, as it does for a record committed a moment later (an empty slot is reported as corruption only if the file,
  read with `pread`, shows it empty for 50 ms: C11). The copying reader (`Reader::open`) reads with `pread`
  and did not fail in any of these runs.
- **Readers after a repair.** A reader whose segment recovery replaced or moved to `quarantine/` returns
  `Error::Discarded` once it notices (on a validation error, after 100 ms of waiting, or at the next segment
  boundary; a durable-only reader also when the checkpoint moves past its cursor); it never silently continues into
  the repaired history. Until then a visible reader may return records that recovery removed, like records lost to a
  power loss (`tests/durable_only.rs::visible_reader_after_a_repair_is_discarded_at_the_old_end`). A durable-only
  reader doesn't: it returns only records covered by a marker that it applied to a file it had just confirmed was
  current, reading them from the file's current bytes (C13).
  A repair in place (storage damage emptied a commit word after the checkpoint and left no committed history that
  recovery can find after it, so recovery zeroes the records from there on in the same file, C11) can't be noticed:
  the file keeps its identity. A visible reader may then return the removed records it had already read or buffered
  and continue in the new history without `Error::Discarded`;
  if its position falls inside a record of the new history it waits there (`Ok(None)`), or returns `Error::Discarded`
  once the checkpoint marker or a later segment shows that its position is not the head and the record it passed last is
  not before it any more (ADR [0050](decisions/0050-empty-slot-in-history.md)), or reports
  `Error::Corrupt` for bytes that aren't corrupt, until the application seeks to its position. (If damage also
  destroyed the checkpoint marker, or set it back to an older one, recovery can remove *covered* records in place, and
  a seek forward in the reader's segment, or to its position, may then go on from that position when the new history
  holds, right before it, bytes that form a record with the sequence number expected there. A seek to the last record
  the reader passed, or an earlier one, scans the segment, and so does a new reader: ADR
  [0046](decisions/0046-seeks-that-need-no-index.md).) A reader with `ReaderConfig::seek_index` may also enter a segment
  after the damage and before the repair at a record behind it, where another reader's scan would have stopped; what
  follows is what follows for a reader that was already there (C15, ADR
  [0045](decisions/0045-sparse-seek-index.md) → T7). It returns a record
  that isn't in the journal only if the new history holds, at that position, bytes forming a frame with a valid
  checksum and the expected sequence number. Except for that case, durable-only readers are unaffected (ADR
  [0034](decisions/0034-durable-only-reads-check-segment-identity.md) → In-place repairs).
- **Missing segments.** If the checkpoint marker's segment, or a segment in the middle of the chain, is missing,
  the writer refuses to open (under every recovery policy) rather than discard history on its own. So it does when the
  marker's segment is there but its records do not reach the marker's position (segments restored from an older
  backup than the marker, or the last covered record damaged; C11, ADR 0056); `status` reports that case as
  `dangling` and retention removes nothing then (C14). When the marker is at the first slot of
  its segment, the segment before it is not read: a predecessor that lacks records the marker covers is not detected
  at open, nor by `status` (`verify` and readers report it, and retention stops at its seal; the writer appends only
  after it, in the marker's segment, where a reader that seeks there reads the new records; ADR 0056, amendment:
  `tests/marker_position.rs::a_marker_at_offset_64_after_a_predecessor_that_lacks_records_opens`). A reader that
  reaches a seal and does not find its successor, while its own segment is still in place, reads that slot again
  from the file. If the seal is still there, it tries the successor once more, and reports
  `CorruptReason::BrokenChain` only if that attempt misses too
  (`tests/retention.rs::missing_successor_with_segment_in_place_is_a_broken_chain`); a later call tries again, and
  succeeds once a recovery has put the successor in place. If its own segment is gone too, retention removed both
  and it reports `Error::Discarded` (C14). If the seal is gone from the file, the reader can't tell why, and reads
  the slot as it is now, like a reader that never read the seal: it waits there or continues with what is written
  there next. That is what happens when storage damage removed a seal, and recovery kept its segment in place and
  moved the successor into `quarantine/`, after the reader read the seal or while the safe reader held it in its
  buffer: the whole seal zeroed in front of a successor that no longer opens, or a zeroed stretch from the start of
  a record after the checkpoint through the end of the seal (`format.md` → What readers do about repairs;
  `tests/durable_only.rs::visible_reader_does_not_follow_a_seal_removed_in_place`). Where the damage began earlier
  in the segment than the seal, the reader's position may fall inside a record of the new history, as for any reader
  across an in-place repair (C11). The re-read happens only when the successor is not found: a successor
  that a new history has created again at the same base opens at the first attempt, and the reader follows its
  buffered seal into it, which C11 allows across an in-place repair.
- **CRC32C** detects all burst errors up to 32 bits and most other corruption, not all of it. It is not a
  cryptographic integrity check.
- **Clocks.** Timestamps are caller-supplied data. tickertape never orders or validates by timestamp.
- **`flock`** works on local filesystems. On network filesystems it may silently fail to exclude other hosts; they
  are not supported.
- **The writer lock and `fork`.** The lock is a `flock`, which belongs to the open file description of
  `writer.lock`: closing a descriptor releases it only when the last copy of that descriptor closes, and a child
  forked by any thread holds a copy until it calls `exec` (the descriptor is close-on-exec) or exits. Dropping the
  writer in the process that opened it releases the lock explicitly (after its helper threads have stopped and
  readers have been told it has gone), and so does an open that fails after taking the lock, so neither waits for
  such a child. When the writer's process exits or dies without dropping the writer, the lock stays with the last
  copy of the descriptor: a child keeps the journal locked until it execs or exits, briefly for a child that is about
  to run a program, but for its whole life for one that never execs (a pre-fork worker; Python `multiprocessing` with
  the fork start method), and the same holds for a grandchild. A new writer sees `Error::Locked` meanwhile (C3). A
  forked child must neither use nor drop an inherited writer. If it drops one, the explicit unlock is skipped and the
  lock stays with the parent, and the child closes its copy of the lock descriptor first and neither joins the
  spare-segment thread nor removes a prepared spare. The rest of the writer's clean-up still runs in the child:
  stopping the prefault helper, whose thread does not exist there, can stall it, and clearing the wake-up region
  disturbs the parent's readers.
